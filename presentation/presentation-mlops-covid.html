Prédire le COVID à J+7 01 / 19
Le problème Contexte

Anticiper une semaine à l’avance, avec ce que l’on sait aujourd’hui

  • La question posée. À partir de l’historique connu le jour J, estimer le nombre de cas qui sera publié le jour J+7.
  • Pourquoi sept jours. C’est le délai utile : une semaine suffit pour ajuster une capacité de dépistage, un planning hospitalier ou une campagne de rappel, et reste assez court pour que le passé récent porte de l’information.
  • La contrainte de rigueur. Aucune variable postérieure au jour J ne doit entrer dans le modèle, sous peine de fuite temporelle — une erreur qui produit d’excellents scores et un modèle inutilisable.

Formulation

Régression supervisée sur série temporelle. Une ligne = un jour. La cible est la valeur observée sept jours plus tard.

Ce que ce n’est pas

Pas un modèle épidémiologique compartimental (SIR, SEIR). Pas un modèle causal : il apprend des régularités statistiques, il n’explique pas la transmission.

Résultats · métriques07 / 19
Résultats Prédit vs réel

Le modèle a compris le rythme, pas encore l’amplitude

Le rythme est juste. Les pics prédits tombent exactement les jours de publication : la périodicité hebdomadaire est parfaitement restituée.

L’amplitude est surestimée. Sur les treize publications, la prédiction dépasse le réel à chaque fois — le modèle reste ancré sur les niveaux, plus élevés, vus à l’entraînement.

Puis plus rien. La France cesse toute publication après le 18 juin 2023 : les 189 derniers jours du test sont des zéros que le modèle prédit sans effort.

Mise en service · API12 / 19
Versioning DVC · MinIO · MLflow

À partir d’un modèle, retrouver ses données et son code

DVC — les données et le modèle

  • Un pipeline en trois étapes : ingest, prepare, train.
  • dvc.lock garde l’empreinte de chaque fichier, de chaque script et des paramètres : un commit git désigne une version exacte du code, des données et du modèle.
  • dvc repro ne rejoue que les étapes dont une entrée a changé ; dvc push envoie les fichiers dans MinIO, un stockage compatible S3.

Retour arrière : git checkout puis dvc checkout.

MLflow — le lien entre modèle et données

  • Chaque entraînement enregistre ses 9 paramètres et ses 2 métriques, MAE et RMSE.
  • Il enregistre aussi le jeu de données utilisé, son empreinte DVC et le commit git.

Registre de modèles MLflow · Airflow

Un modèle n’entre en production que s’il fait au moins aussi bien

MLflow — un cycle de vie porté par deux alias

  • candidate : la dernière version entraînée, à valider.
  • production : la version servie par l’API.
  • Le candidat et la production sont évalués sur le même jeu de test ; le candidat ne passe que si sa MAE est inférieure ou égale. Chaque version porte son verdict : promu, rejeté, remplacé.

Les alias remplacent les étapes Staging / Production, que MLflow a dépréciées. Retour arrière : déplacer l’alias production, puis appeler POST /model/reload.

Airflow — le DAG retrain_covid_model

  • Six tâches : ingest_data, prepare_data, train_model, promote_model, version_artifacts, reload_api.
  • Planifié @weekly, à la cadence de publication des données ; déclenchable à la main.
  • reload_api fait charger la nouvelle production à l’API, sans redémarrage.

Monitoring Prometheus · Evidently · Airflow

Surveiller le service, surveiller le modèle, réagir seul

Prometheus — le service

  • L’API expose /metrics, collecté toutes les 15 secondes : requêtes, temps de réponse, prédictions par version du modèle.
  • 7 règles d’alerte : API indisponible, aucun modèle chargé, taux d’erreur, latence, dérive, performance dégradée, monitoring en retard.
  • Alertmanager regroupe les alertes et les achemine ; Grafana les affiche.

Le canal de notification (mail, Slack) reste à brancher.

Evidently — le modèle

  • Chaque prédiction est journalisée avec ses entrées.
  • Dérive : alerte si au moins la moitié des variables ont changé de distribution par rapport à l’entraînement.
  • Performance : les prévisions datées sont rapprochées de la valeur observée à J+7 ; alerte au-delà de 1,5 fois l’erreur relative de référence.
  • Le DAG monitor_covid_model tourne @daily et relance l’entraînement si nécessaire.

Démonstration En direct · ~7 minutes

La chaîne en fonctionnement, du démarrage au réentraînement

  1. docker compose up -d
    Les huit conteneurs démarrent ensemble : API, MLflow, MinIO, Airflow, Prometheus, Alertmanager et Grafana.
  2. Swagger sur :8000/docs
    L’API se documente seule : les onze champs attendus, leurs types et un exemple pré-rempli.
  3. GET /health
    Le modèle répond avec sa propre carte d’identité : version, origine (le registre), pays, horizon, MAE et RMSE.
  4. POST /predict sans clé → 401
    La protection se vérifie en une requête : sans en-tête x-api-key, rien ne passe.
  1. POST /predict avec la clé → 200
    Sur la charge utile d’exemple, le modèle renvoie 5 300,66 cas à J+7.
  2. MLflow sur :5000
    Les runs côte à côte, et dans l’onglet Models les versions avec leurs alias candidate et production.
  3. Airflow sur :8080 → Trigger DAG
    retrain_covid_model se déclenche à la main ; ses six tâches passent au vert, de l’entraînement à la promotion.
  4. Grafana sur :3000
    Après un trafic de démonstration et le DAG monitor_covid_model, la dérive apparaît sur le tableau de bord et l’alerte dans Alertmanager.

Regard critique Limites

Six limites que nous assumons

  1. La cadence hebdomadaire n’est pas traitée. Travailler sur une série « quotidienne » composée à 88 % de zéros rend les métriques globales flatteuses et peu informatives.
  2. Six variables sur onze sont inertes. lag_1 à lag_6 ne portent aucune information : le modèle en supporte le coût sans aucun bénéfice.
  3. Surestimation systématique en décrue. Sur les treize publications testées, l’erreur relative moyenne atteint 82 %.
  1. Tout tourne sur une seule machine. MinIO, MLflow et Airflow partagent le même poste : ni sauvegarde distante, ni reprise si la machine tombe.
  2. L’authentification est minimale. Une seule clé, partagée par tous les clients, sans expiration.
  3. Les alertes n’ont pas de destinataire. Elles sont déclenchées, regroupées et routées, mais aucun canal (mail, Slack) n’est branché.

Ces limites ne sont pas des oublis : elles ont été identifiées en analysant les résultats, et c’est cette analyse qui a produit les diapositives 04, 09 et 10.

Regard critique18 / 19
Conclusion Prochaines étapes

La chaîne tient ; c’est le signal qu’il faut maintenant redresser

Sur la modélisation

  • Rééchantillonner en pas hebdomadaire. Une série de 201 points denses remplacerait 1 387 points dont 88 % de zéros — les décalages redeviendraient tous porteurs d’information.
  • Évaluer sur les seuls jours de publication, et publier systématiquement l’écart à une référence naïve.
  • Valider par TimeSeriesSplit plutôt que par un unique découpage, et comparer la forêt à une régression régularisée et à un gradient boosting.

Sur l’industrialisation

  • Brancher un canal de notification sur Alertmanager, mail ou Slack.
  • Héberger le stockage et le registre : un S3 et une base MLflow hors du poste, sauvegardés ; pour DVC, seule l’adresse change.
  • Renforcer l’authentification : un jeton par client, à durée limitée (OAuth2 et JWT).
  • Prolonger l’intégration continue jusqu’au déploiement, et couvrir la chaîne de réentraînement par un test de bout en bout.

L’infrastructure MLOps est en place et fonctionne de bout en bout. Le travail restant porte désormais sur la donnée et sur l’évaluation — c’est-à-dire sur ce qui fait la valeur d’une prévision.
